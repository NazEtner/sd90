# sd90-rs

<p>
<img src="../assets/trademarks/asio-compatible.png" alt="ASIO Compatible" width="120">
</p>

EDIROL SD-90 (Roland Studio Canvas) を WinUSB 経由でユーザーモードから扱うクレートです。

* `sd90_asio.dll` … ASIO® ドライバ (入出力 2ch)
* `sd90-rs.exe` … 記述子ダンプ / iso 取り込み / ASIO 自己検証のためのプローブ
* `usbmidi` … IF2 の MIDI エンドポイント (音源に MIDI を渡す唯一の経路)

SMF を読み込んで曲を再生する機能は別クレート [`sd90-seq`](../sd90-seq) にあります。
このクレートが扱うのは、デバイスを操作する層までです。

カーネルドライバは一切書いていません。そのため、カーネル署名も EV 証明書も不要です。

## カーネルドライバを使わない理由

- Roland 純正ドライバ (`rdif1016.inf` / `Rdwm1016.sys`, 2007年) は
  VeriSign Class 3 Code Signing 2004 CA による SHA-1 署名のため、現行 Windows の
  カーネルコード整合性チェックを通りません。実機では `STATUS_INVALID_IMAGE_HASH (0xC0000428)` になります。
  セキュアブートや HVCI を無効にしても結果は同じです (x64 のカーネル DSE は常に有効なため)。
- Generic モード (PID 0x0017) では標準の `usbaudio.sys` が割り当てられますが、
  `STATUS_DEVICE_CONFIGURATION_ERROR (0xC0000182)` で起動に失敗します。
  AudioControl の `bInCollection` が MIDIStreaming インタフェース (IF3) を
  列挙しておらず、UAC1 の仕様に違反していることが原因と考えられます。
- `winusb.sys` は Microsoft の署名済みなので、こちらのコードには
  カーネル署名が一切必要ありません。そのため、すべてユーザーモードで処理しています。

## 実機から読み出した記述子 (Vendor モード, PID 0x0016)

Full Speed (USB 1.1)、3 インタフェース、`bDeviceClass=0xFF` (非コンポジット) です。

```
IF0  再生 (host -> SD-90)   class FF/02
     alt0 = エンドポイント無し
     alt1 = EP 0x01 OUT  iso  sync=None  wMaxPacketSize=320  bInterval=1
IF1  録音 (SD-90 -> host)   class FF/02
     alt0 = エンドポイント無し
     alt1 = EP 0x81 IN   iso  sync=None  wMaxPacketSize=320  bInterval=1
IF2  MIDI                   class FF/FF
     alt0 = EP 0x02 OUT / 0x82 IN  bulk 32B
     alt1 = EP 0x02 OUT bulk / 0x82 IN interrupt  32B
```

両ストリームとも `FORMAT_TYPE_I`、PCM、2ch、24bit、48000Hz 固定 (離散値 1 個) です。
クラスコードは 0xFF ですが、記述子の中身は UAC1 そのものです。

`sync type = None` なので、**フィードバックエンドポイントは不要**です。
帯域は 320B/frame × 2 方向で、フルスピードの iso 帯域に対して十分な余裕があります。

### 実測で確認できたこと (3 秒 x 2 回, いずれもエラー 0 / 取りこぼし 0)

- **ペイロードは 24bit リトルエンディアン / 2ch インタリーブの生 PCM で、独自ヘッダはありません。**
  記述子の `bSubframeSize=2` は単なる誤りで、実際は 3 バイト/サンプルです。
  288 byte = 48 sample x 2ch x 3 byte とぴったり一致します。
- **実効レートはちょうど 48000 Hz** です (平均 48.000 サンプル/パケット)。
- **パケット長は 282 / 288 / 294 の間で揺れます** (47 / 48 / 49 サンプル)。
  sync=None の自走クロックなので、ホストの 1ms フレームとは同期していません。
  282 と 294 の出現回数はほぼ同じで、平均すると 48.000 に落ち着きます。
  → **ASIO 化する際は「1ms = 48 サンプル固定」を前提にしてはいけません。**
  USB 側と ASIO バッファの間にリングバッファを挟む必要があります。
  なお、3 つとも 6 の倍数なので、フレームの境界が途中で割れることはありません。

- **録音バスには内蔵音源の音が乗ります。** 音源を鳴らしながら取り込むと、ピークが
  -4 dBFS 前後まで上がります。本体側の設定だけで完結しており、ベンダリクエストの
  解析は必要ありませんでした。

### ハマった点: パケット記述子の Offset は転送ごとの相対値

`USBD_ISO_PACKET_DESCRIPTOR.Offset` は、**登録したバッファの先頭からの絶対値ではなく、
その転送に渡した offset からの相対値**です。どのスロットでも `0, 320, 640, ...` が返ってきます。

```
let off = slot * slot_bytes + d.Offset as usize;   // 基点を足すこと
```

これを足し忘れると、常にスロット 0 の領域を読み続けることになります。厄介なのは、その状態でも

- パケット記述子の `Status` はすべて 0
- パケット長も 288 で正常
- 平均サンプル数も 48.000 のまま

と、統計上はまったく正常に見えることです。**症状は波形の不連続としてしか現れません。**
転送境界 (8 パケット = 384 サンプル) の 13〜30% で波形が飛ぶことから発覚しました。
修正後は 0.3% (音楽的な過渡音と区別がつかない水準) まで下がっています。

`SD90_DEBUG_DESC=1` を設定すると最初の 6 転送分の記述子を出力するので、
同種の問題が疑われる場合は、まずこれを確認してください。

### 未解決の点

- 録音バスに何が混ざっているか (音源出力のみか、アナログ入力も加算されるか) は、
  本体のミキサー設定によって変わります。無信号時にも -75 dBFS 程度のノイズフロアと
  チャンネルごとの DC オフセットが乗っているため、アナログ系も加算されていると思われます。

## MIDI (IF2)

**MIDI StartUp を USB にしないと、MIDI は USB に出てきません。また、その設定では背面の
MIDI IN は音源に届きません** (ホストに転送されます)。つまり、音源に MIDI を渡す
経路は USB しかありません。実際に EP 0x82 を読むと、DIN に入力した演奏が cable 2 の
パケットとして流れてきます。

クラスコードは 0xFF ですが、中身は標準の USB-MIDI 1.0 です。Linux の
`sound/usb/quirks-table.h` にある 0582:0016 の項目も、そのように定義しています:

```
QUIRK_DATA_MIDI_FIXED_ENDPOINT(2) {
        .out_cables = 0x000f,
        .in_cables  = 0x000f
}
```

実測で確認した cable の割り当ては次のとおりです。

| cable | 宛先 |
| --- | --- |
| 0 | PART A (内蔵音源) |
| 1 | PART B (内蔵音源) |
| 2 / 3 | 背面の MIDI OUT コネクタ |

Identity Request を送ると応答が返ってくるので、音を鳴らさずに疎通を確認できます:

```
送信 F0 7E 7F 06 01 F7
受信 F0 7E 10 06 02 41 48 01 00 00 00 00 00 00 F7   (41h = Roland)
```

### ハマった点: 生の MIDI バイト列を書き込んではいけない

エンドポイントに書き込めるのは **4 バイトのパケットだけ**です。生のバイト列をそのまま
書き込むと先頭バイトが CIN として解釈され (`F0 7E 7F 06` なら cable 15 / CIN 0 の
未定義パケット)、SysEx の終端 F7 が届かないまま、パーサが待ち状態に入ってしまいます。
**そうなると、以後のノートはすべて飲み込まれ、エラーも出ません。** 転送自体は
デバイスが ACK を返すので、WinUSB 側からは成功したように見えます。

元に戻すには、Native On を送るか、本体の電源を入れ直してください:

```
F0 41 10 00 48 12 00 00 00 00 00 00 F7
```

なお、GM1 System On / GS リセット / Native On のどれを送っても、音は出続けます
(同じ和音で -12.3 / -15.0 / -19.9 / -16.1 dBFS)。モードの切り替え自体が
無音の原因になることはありません。

## MIDI の送出タイミング

DAW から音源を鳴らす以上、「いつ送ったか」が音楽的な精度を左右します。基準にできる
のは**取り込み済みのフレーム数** (`Shared::frames_captured`) だけで、ホストの
`Instant` は使えません。SD-90 の水晶とホストの時計は ppm 単位でずれており、数分で
数十 ms の差が積み重なるためです。フレーム数の更新は 1 転送に 1 回しか来ないので、その間だけホストの
時計で補間します。位相はデバイスのクロックで合わせ、その間をホストの時計で埋める形です。

### 転送の粒度がそのまま時計の粒度になる

`sd90-rs latency` は、「このデバイスフレームで送る」と予約したノートが、実際に
取り込み側に現れるまでのフレーム数 `d` を測定します。取り込みの転送粒度だけを変えて
同じ測定をした結果は次のとおりです:

```
8 パケット/転送 (8ms):  d 中央値 7.33ms   ばらつき 3.60〜8.77ms   (8 回)
1 パケット/転送 (1ms):  d 中央値 3.38ms   ばらつき 3.33〜3.46ms   (16 回)
```

差の 4.0ms は、8ms の更新間隔による**平均的な遅れ (間隔の半分)** にちょうど一致します。時計は最後の更新から
の経過時間で外挿しているため、更新の粒度がそのまま系統的な遅れとして加わり、その範囲内で
ランダムに揺れます。1ms 粒度にすると遅れが消えるだけでなく、ばらつきも 5.2ms から
**0.13ms** まで小さくなります。

つまり、`d = 162 フレーム (3.38ms)` が音源そのものの応答時間で、8ms 構成で見えていた
残りの遅れは、すべてこちらの時計の粗さによるものでした。MIDI を送出する側では `StreamCfg::capture_only`
(1ms 粒度) を使ってください。転送の本数は 125/s から 1000/s に増えますが、OUT 側はもともと
1000/s で回しているので、負荷の桁は変わりません。

ASIO ドライバについては、下の「ASIO ドライバ」節の実測値が 8 パケット/転送の構成で取ったものなので、
既定値は 8 のままにしています。

## 準備

1. 本体パネルの [SYSTEM] → [PAGE] で 5 ページ目を表示し、V1 で **USB Driver** を
   **Vender** (マニュアルの表記のまま) にして [ENTER] を押します。同じ画面の 2 ページ目にある
   **MIDI Start Up** も **USB** にしておいてください (下の MIDI 節を参照)。
   USB Driver の変更は次回の電源投入から有効になるので、電源を入れ直します (PID 0x0016)。
   (Owner's Manual p.69-70, p.74。背面にモードスイッチはありません)
2. [Zadig](https://zadig.akeo.ie/) で `EDIROL SD-90` に **WinUSB** を割り当てます。
   - Options → List All Devices
   - USB ID が `0582 0016` のものを選びます (`0017` は Generic モード側なので注意してください)
   - Replace Driver

Zadig で WinUSB を割り当てるまでは、`list` には何も表示されません。純正ドライバは起動に失敗しており、
デバイスインタフェースが有効にならないため、SetupAPI から見えないのが正常です。
なお、純正ドライバはどのみち署名の問題で動作しないので、置き換えても失うものはありません。
元に戻したい場合は、デバイスマネージャーの「ドライバーを元に戻す」で戻せます。

## ASIO ドライバ

`sd90_asio.dll` が ASIO ドライバの本体 (in-proc COM サーバ) です。入出力とも 2ch です。

当初は入力専用 (outputs=0) で作っていましたが、**SONAR (Cakewalk) は `getChannels` で
出力が 0 だと分かった時点で処理を打ち切る**ことがログから判明したため、出力も実装しました。
Cubase は outputs=0 でも問題なく動作していたので、これはホストに依存する要求です。

| 項目 | 値 |
| --- | --- |
| チャンネル | 入力 2 / 出力 2 |
| サンプル形式 | `ASIOSTInt32LSB` (24bit を 8bit 左シフトして格納) |
| サンプルレート | 48000Hz 固定 |
| バッファ | min 128 / preferred 512 / max 8192, 2 の冪のみ |
| レイテンシ申告 | 入力 bufferSize+384 / 出力 bufferSize+助走+USBキュー |
| クロック | SD-90 内蔵 (自走)。ホストではなくデバイスがマスタ |

x64 専用です。32bit のホストからは見えません。

### 登録

管理者権限のコンソールで、リポジトリのルートから次のように実行します:

```
regsvr32 target\release\sd90_asio.dll
regsvr32 /u target\release\sd90_asio.dll
```

DLL の**パスは登録時に記録される**ので、登録後に DLL を移動した場合は登録し直してください。
登録先は `HKLM\SOFTWARE\ASIO\SD-90 (WinUSB)` と `HKCR\CLSID\{7E1A5C42-...}` です。

### 出力側の実装

`WinUsb_WriteIsochPipeAsap` は**パケット記述子を受け取りません**。WinUSB がバッファを
`wMaxPacketSize` (320B) ごとに区切ってしまうため、288B のパケットを作るには
**1 転送 = 1 パケット = 1 フレーム**にするしかありません (転送は 1000 本/秒になります)。

その代わり、1ms 単位でパケット長を選べるので、ホストのフレームクロックと
デバイスの水晶の ppm 単位の差を、47/48/49 サンプルの出し分けで吸収しています。
これは、SD-90 が入力側でホストに対して行っているのと同じことです。

出力レートがデバイスのクロックに追従するのは、**入力で受け取ったフレーム数と同じだけを
出力に流している**からです。入出力は同じ水晶で動いているので、これだけで同期が取れます。

#### サーボは必ず平滑化した値で回すこと

リングの瞬間的な滞留量は、「ホストが bufferSize 分を一度に積む」「USB が 8ms ごとに
384 フレームをまとめて取り出す」ことで常に大きく上下しており、**その揺れ自体には意味がありません**。
生の値で 47/49 を判断すると、6 割のフレームで長さが変わるほど不安定になり、
1 秒に 1 回ほど再生波形の振幅が飛びます。時定数 1 秒の EMA を挟むと、
調整は 5% 程度に落ち着き、振幅の飛びもなくなります。

実測結果 (440Hz -12dBFS を出力し、SD-90 のモニタ経由で入力に戻して測定):

```
生値サーボ : servo47=3367 servo49=3056 / 10s   振幅の飛び 6 窓
EMA サーボ : servo47= 470 servo49= 225 / 15s   振幅の飛び 0 窓
              underrun=0 overrun=0
              包絡の中央値 0.2499 (送出値と一致), 基本波 440.4Hz,
              ゼロ交差間隔 109.09±0.29 (理論 109.09)
```

### ASIO の注意点

* ホストは `CoCreateInstance(clsid, .., **clsid**, ..)` のように、**IID に CLSID を渡してきます**。
  QueryInterface で CLSID も受け付けないと、インスタンスを生成できません。
* vtable は IUnknown の 3 メソッドと ASIO の 20 メソッドが並ぶだけです。
  x64 では呼び出し規約が 1 つしかないので、`extern "system"` で一致します
  (x86 の `__thiscall` の問題は考えなくて構いません)。
* Windows 版の ASIO SDK は `NATIVE_INT64=0` なので、`ASIOSamples` /
  `ASIOTimeStamp` は `{hi: u32, lo: u32}` の 2 ワード構成です。u64 をそのまま
  書き込むと、上位と下位が入れ替わってしまいます。

## 使い方

```
sd90-rs list                     WinUSB から見える SD-90 を探す
sd90-rs desc                     デバイス/コンフィグ記述子をダンプ
sd90-rs capture [ms] [out.raw]   IF1 / EP 0x81 から iso IN を取り込む
sd90-rs asiotest [ms]            ASIO ドライバをレジストリ登録なしで検証
sd90-rs latency [回数] [ch] [note]  音源の応答 d を実測する
```

`latency` は、既定では ch 10 (ドラム) の note 38 を 8 回鳴らし、送出フレームと
発音の立ち上がり (オンセット) との差を一覧表示します。プラグイン ([`sd90-vst`](../sd90-vst)) が申告するレイテンシ `L = B + d` の `d` は、これで決めています。
立ち上がりの遅い音色を指定するとアタック分が `d` に含まれてしまうので、打楽器で測定してください。

`asiotest` は、DllGetClassObject → クラスファクトリ → IASIO という一連の経路を、
管理者権限も DAW も使わずに呼び出します。vtable はホスト側の宣言を独自に書き起こして
いるので、ドライバ側の定義とずれていれば、すぐに異常として現れます。

* `SD90_TONE=1` … 出力に 440Hz -12dBFS の正弦波を流し、入力を `asiotest_in.i32`
  (i32 LE インタリーブ) に記録します。SD-90 のモニタ経由で入力に戻ってくるので、
  出力が正しいかどうかを入力側で測定できます。
* `SD90_REC=1` … トーンを出さずに、入力だけを記録します (切り分け用)。

`capture` は、生のパケットペイロードをそのまま連結して書き出します。あわせて、次の情報を表示します。

- パケット長のヒストグラム (288 に揃っているか)
- 取得できたバイト数から逆算した実効レート (48000 付近になっているか)
- 24bit LE / 2ch と仮定した場合のピークレベル (無音になっていないか)
- 先頭パケットの hex

上の「実測で確認できたこと」は、これを使って調べました。

## 構成

| ファイル | 役割 |
| --- | --- |
| `src/device.rs` | SetupAPI でのデバイス探索、WinUSB オープン、IF0/1/2 のハンドル |
| `src/descriptor.rs` | 記述子の取得と UAC1 として解釈した表示 |
| `src/iso.rs` | プローブ用の一括取り込みと統計 (`capture_with` で外から時計を読める) |
| `src/usbmidi.rs` | IF2 の bulk。USB-MIDI 4 バイトパケットの組み立てと送受信 |
| `src/midisched.rs` | デバイスフレーム基準の MIDI 送出。時計とキューと送出スレッド |
| `src/latency.rs` | 音源の応答 `d` の実測 |
| `src/ring.rs` | USB 側と ASIO 側をつなぐ SPSC リングバッファ |
| `src/stream.rs` | iso IN / OUT を回し続けるワーカ |
| `src/asio.rs` | IASIO 実装と RT スレッド |
| `src/comserver.rs` | クラスファクトリ、DLL エクスポート、自己登録 |
| `src/asiohost.rs` | `asiotest` 用の最小 ASIO ホスト (bin 側のみ) |
| `src/log.rs` | 診断ログ (既定は無効) |

DAW の中では stdout を使えないため、診断情報は `%TEMP%\sd90_asio.log` に出力します。
**空のファイルを自分で作成すると有効になり、ファイルが無ければ何も出力しません。**
ホストがどこまで呼び出して処理を諦めたかを確認するのに使います (SONAR の件もこれで判明しました)。

iso 転送は 8 スロット × 8 パケット (= 64ms 先まで) を積んだ状態で回しています。
USB スレッドと ASIO の RT スレッドは、どちらも MMCSS の "Pro Audio" を取得します。

データの流れ:

```
USB スレッド                  リング                 RT スレッド              ホスト
iso IN 8ms 分を回収 ---> 24bit 詰めのまま ---> bufferSize 溜まったら ---> bufferSwitch()
(連結以外の仕事をしない)   (16384 フレーム)      deinterleave + <<8         |
                                                                            | 出力を埋める
iso OUT 1ms ずつ送出 <--- 24bit 詰めのまま <--- 同じフレーム数を畳む <-------+
(EMA サーボで 47/48/49)   (助走 = bufferSize x2,  >>8 して interleave
                           最低 1024)
```

パケット長が揺れる以上、USB の到着単位を ASIO のバッファサイズに直接
対応させることはできません。リングバッファで両者を切り離すことが要点です。
